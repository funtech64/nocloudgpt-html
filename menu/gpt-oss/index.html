Overview & Purpose

As organizations integrate large language models into customer-facing products, internal tooling, and decision-support systems, the need for reliable, auditable content moderation has become mission-critical. Public API-based safety services — whether bundled into a cloud AI provider or offered as standalone classification endpoints — introduce a fundamental tension: every piece of flagged content, every user message, every sensitive query is transmitted off-premise and processed by infrastructure outside your control.

GPT-OSS Safeguard resolves this tension entirely. It is an open-source safety classification model designed to serve as an inline guardrail layer within LLM pipelines, inspecting both user inputs and model outputs before they are processed or returned. Unlike rule-based content filters that rely on keyword blocklists or regex patterns, GPT-OSS Safeguard applies learned semantic understanding to detect nuanced policy violations, contextual harm, and sensitive data exposure — the categories that keyword filters almost always miss.

When deployed through NoCloudGPT via Ollama, GPT-OSS Safeguard runs entirely within your AWS Lightsail instance, private VPC, or on-premise server. No content classification request ever leaves your perimeter. Audit logs stay in your SIEM. Flagged outputs remain under your governance.

How GPT-OSS Safeguard Works

GPT-OSS Safeguard is a fine-tuned transformer model trained on curated safety datasets spanning multiple harm categories. Its architecture is optimized for classification inference rather than generative tasks, which allows it to reach production-useful latencies even on quantized CPU deployments. The model accepts a structured prompt containing the content to be evaluated alongside an optional policy context block, and returns a structured label with an associated confidence score.

Harm Taxonomy & Classification Categories

Out of the box, GPT-OSS Safeguard classifies content across a broad taxonomy of harm categories that aligns with established AI safety frameworks:

  • Violence & Physical Harm — direct incitement, graphic violence, self-harm
  • Hate Speech & Discrimination — protected characteristics, targeted harassment
  • Sexual Content — explicit material, CSAM detection signals
  • Privacy & PII Exposure — SSNs, financial identifiers, health data
  • Misinformation — factual deception, fabricated citations
  • Cybersecurity Threats — malware generation, exploit guidance
  • Controlled Substance Facilitation — drug synthesis, illegal procurement
  • Weapons & Dangerous Materials — explosive, biological, chemical
  • Regulatory Non-Compliance — UPL, unlicensed medical advice
  • Custom Policy Violations — injected via prompt-based policy context

Prompt-Based Policy Injection

A key differentiator of GPT-OSS Safeguard is its support for prompt-based policy injection — the ability to define custom content rules at inference time without retraining the model. Organizations can prepend a policy context block describing domain-specific rules (for example, a financial services firm's prohibition on specific instrument recommendations, or a healthcare platform's restrictions on diagnostic language), and the model will apply those rules alongside its baseline harm taxonomy.

Key Insight: Prompt-based policy injection means your content moderation rules can be versioned, audited, and updated in your policy management system — not buried in a model fine-tuning run. Legal and compliance teams can review plain-language policy definitions without interpreting neural network weights.

Dual-Layer Interception

GPT-OSS Safeguard is designed to operate at two points in an LLM pipeline:

Input screening (pre-inference): User messages are classified before reaching the primary LLM. Prompts flagged above a configurable confidence threshold are blocked, redirected, or logged — preventing the primary model from being weaponized for harmful content generation in the first place.

Output screening (post-inference): Model responses are classified before being returned to the user or downstream system. This catches cases where a well-intentioned prompt elicits a policy-violating response from the primary LLM — a failure mode that input screening alone cannot prevent.

The 7B parameter base model represents the recommended production configuration, offering a strong balance between classification accuracy and inference speed. Smaller 3B variants are available for high-throughput, latency-critical deployments where the full taxonomy breadth is not required.

Python Integration — Inline Guardrail Class

import requests import json from dataclasses import dataclass from typing import Optional OLLAMA_BASE = "http://localhost:11434/api/generate" SAFEGUARD_MODEL = "gpt-oss-safeguard:7b-q4" SYSTEM_POLICY = """ You are a content safety classifier. Evaluate the provided text against the policy context and return a structured JSON classification. Categories: violence, hate_speech, sexual, pii, misinformation, cybersecurity, controlled_substances, weapons, regulatory, custom_policy, safe """ @dataclass class ClassificationResult: safe: bool category: str confidence: float flagged_content: Optional[str] = None class GPTOSSSafeguard: def __init__(self, policy_context: str = ""): self.policy_context = policy_context def classify(self, text: str) -> ClassificationResult: prompt = ( f"[SYSTEM]{SYSTEM_POLICY}\n" f"[POLICY]{self.policy_context}\n" f"[CONTENT]{text}\n" f"[OUTPUT] Return JSON only." ) response = requests.post( OLLAMA_BASE, json={"model": SAFEGUARD_MODEL, "prompt": prompt, "stream": False} ) raw = response.json()["response"] result = json.loads(raw) return ClassificationResult( safe=result.get("safe", True), category=result.get("category", "safe"), confidence=result.get("confidence", 0.0), flagged_content=result.get("flagged_content") ) # — Example Usage — custom_policy = """ ADDITIONAL RULES: - Flag any mention of specific competitor product names. - Flag any promise of guaranteed investment returns. - Flag requests for off-platform communication. """ guard = GPTOSSSafeguard(policy_context=custom_policy) result = guard.classify( "I can guarantee you a 40% return if you message me directly at my personal email." ) print(f"Safe: {result.safe}, Category: {result.category}, Confidence: {result.confidence:.2f}") # Safe: False, Category: custom_policy, Confidence: 0.94

EU AI Act — High-Risk Application Obligations

The EU AI Act designates AI systems used in healthcare, education, employment, and critical infrastructure as high-risk, triggering mandatory technical documentation, risk management systems, and human oversight requirements. GPT-OSS Safeguard's classification logs — stored locally in your infrastructure — constitute auditable evidence of an operational risk management system as required by Article 9. The prompt-based policy definitions serve as the plain-language technical documentation required by Article 11.

HIPAA Technical Safeguard Alignment

The HIPAA Security Rule requires covered entities and business associates to implement technical security measures to guard against unauthorized access to PHI. When a patient interacts with an AI-powered health portal, their messages may contain PHI. GPT-OSS Safeguard's PII detection category — deployed privately via NoCloudGPT — provides an automated mechanism to identify and flag PHI in AI pipeline traffic without routing that data through a third-party classifier, which would itself require a Business Associate Agreement and introduce additional breach surface.

Important: GPT-OSS Safeguard is a technical control layer, not a legal compliance certification. Organizations in regulated industries should engage qualified legal counsel and compliance specialists to assess how private AI deployment integrates into their overall compliance program.
