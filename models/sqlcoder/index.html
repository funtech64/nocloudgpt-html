SQLCoder: Natural Language to SQL Without Sending Your Schema to the Cloud

Text-to-SQL is one of the highest-value AI use cases for data teams — and one of the highest-risk when routed through a cloud API. Translating a natural language question into a correct SQL query requires the model to understand your database schema: table names, column names, relationships, and data types. That schema is a precise map of your data architecture. Sending it to a third-party API on every query is a data governance problem that most organizations have not fully reckoned with.

SQLCoder, developed by Defog AI, is the leading open-source text-to-SQL model, purpose-trained to generate accurate SQL from natural language questions against real database schemas. Available in 7B and 15B variants via ollama run sqlcoder, it runs entirely on-premise — your schema stays on your network, your queries never leave your environment, and your data team gets natural language database access without the compliance exposure of cloud-routed alternatives.

What SQLCoder Does Well

  • Accurate text-to-SQL generation: Purpose-trained on SQL generation tasks rather than general code — produces syntactically correct, semantically accurate queries against provided schemas at a quality level general-purpose models cannot match
  • Schema-aware query construction: Accepts table definitions, column descriptions, and relationship context in the prompt and uses them to generate queries that respect the actual structure of your database
  • Complex query support: Handles multi-table JOINs, nested subqueries, window functions, aggregations, and conditional logic that simpler models flatten or incorrectly structure
  • Multiple SQL dialects: Generates queries compatible with PostgreSQL, MySQL, SQLite, BigQuery, Snowflake, and other major dialects when dialect context is provided
  • Query explanation: Given an existing SQL query, explains what it does in plain language — useful for onboarding, documentation, and cross-team communication
  • Schema documentation: Generates human-readable descriptions of table structures and relationships from provided DDL statements

On the widely cited SQL-Eval benchmark from Defog AI, SQLCoder 15B outperforms GPT-4 on SQL generation accuracy for real-world database schemas — a benchmark result directly relevant to production data team use rather than academic code generation tasks.

Who This Model Family is For

Personal Use

SQLCoder is a useful specialized tool if you occasionally need to query your own databases without memorizing complex SQL syntax. You can describe what you want in plain English (e.g., "show me the top 10 customers by total order value last quarter") and get working SQL back. It is particularly helpful when learning SQL or exploring personal datasets. Keep in mind this is a focused code-generation model — it does not chat, summarize, or act as a general assistant.

Business / Team Use

For teams where analysts, operations staff, or business users need to pull data without waiting on engineering for every report, SQLCoder enables natural-language querying while keeping sensitive database schemas and query patterns entirely on your own infrastructure. It performs best when paired with a clear, well-documented schema. This makes it valuable for organizations that want to democratize data access without compromising data privacy or compliance.

Developer & Technical Use

Developers can use SQLCoder to accelerate query drafting, prototype reporting features, or build natural-language-to-SQL capabilities inside internal tools. It is particularly strong at interpreting complex database schemas and generating accurate joins, aggregations, and filters. Treat its output as a fast first draft — always review generated SQL before running it against production databases, and provide schema context for the most reliable results.

Data Science & Research Use

Data scientists exploring unfamiliar datasets benefit from SQLCoder's ability to quickly translate analytical questions into SQL. It reduces friction when working with complex schemas and supports building reproducible query pipelines. It is not a statistical modeling or general reasoning tool — its value is narrowly focused on turning natural language into correct, executable SQL.

Deployment Tiers and Compute Requirements

Single Analyst — 7B Q4 (4–6GB RAM, CPU or entry GPU)

The 7B variant handles a wide range of text-to-SQL tasks on CPU-only hardware with 4–6GB available RAM. For moderate schema complexity and standard query patterns — SELECT with WHERE, GROUP BY, and single-level JOINs — the 7B model provides reliable output at a hardware cost of zero beyond existing developer machines. Pull with ollama run sqlcoder:7b.

Production Team — 15B Q4 (AWS g4dn.xlarge, T4 16GB VRAM)

The 15B variant is the recommended deployment for production data team use and any schema of meaningful complexity. On an AWS g4dn.xlarge with a T4 GPU, the 15B Q4 model runs at 15–25 tokens per second — fast enough for interactive natural language querying across a team of analysts. The quality gap between 7B and 15B is most pronounced on complex multi-table schemas, nested query requirements, and dialect-specific syntax. For organizations embedding SQLCoder into an analytics product or internal data portal, the 15B model is the version that justifies the integration effort. Reserved instance cost runs approximately $200–280 USD per month. Pull with ollama run sqlcoder:15b.

The Real Cost of Schema Exposure

A database schema is not generic technical information. It encodes your business domain: what data you collect, how you organize it, what relationships matter, and what terminology your organization uses internally. For a healthcare organization, the schema reveals patient data structures. For a financial firm, it reveals transaction and account architectures. For any organization, it reveals the shape of proprietary business logic that competitors and regulators would find informative.

SQLCoder on-premise means schema context never leaves your network. Every natural language query your analysts submit, every table definition included for context, and every generated SQL statement stays within your infrastructure boundary. For organizations subject to HIPAA, SOC 2, PCI-DSS, or internal data classification policies, this is not a feature — it is the baseline requirement for deploying natural language database access at all.
