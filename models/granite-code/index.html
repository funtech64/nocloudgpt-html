The Source Code IP Problem with Cloud AI

GitHub Copilot, Amazon CodeWhisperer, and similar cloud-based code AI tools have a fundamental problem for organizations building proprietary software: every code completion request sends your source code to an external server. Your algorithms, your architecture decisions, your unreleased features — all transmitted to third-party infrastructure to generate a suggestion.

For startups with early-stage intellectual property, defense contractors with controlled technical data, financial firms with proprietary trading algorithms, and enterprises with competitive technology advantages, this is not an acceptable trade-off. The productivity gains from AI-assisted coding are real, but not if they come at the cost of your most valuable assets.

Granite Code running on Ollama through NoCloudGPT infrastructure eliminates this problem entirely. The model runs on hardware you control. Code completions are generated locally. Nothing leaves your network perimeter. Your source code stays proprietary.

IBM reinforces this with what it calls "code-safe" training for Granite Code — the model is trained exclusively on permissively licensed code with documented provenance, addressing both the data transmission concern and the training data IP concern that has made legal departments cautious about AI-assisted development.

Base vs. Instruct Variants

Each Granite Code size is released in two variants. Base models are optimized for fill-in-the-middle (FIM) completion in IDE integrations — they complete code in context without conversational overhead. Instruct models are fine-tuned for natural language instruction following, making them appropriate for chat-based code assistants, code explanation, and review workflows. For IDE plugins like Continue.dev or Aider, the base model delivers lower latency; for chat interfaces, use the instruct variant.

Fill-in-the-Middle: How Granite Code Works in Your IDE

Standard language model completion works left-to-right: given what comes before the cursor, predict what comes next. This works acceptably for autocomplete but fails for the most common editing pattern in real development — inserting code in the middle of existing functions.

Fill-in-the-middle (FIM) trains the model to use both prefix and suffix context. Granite Code sees what comes before the cursor and what comes after it, then generates the insertion that makes the complete code block logically consistent. This dramatically improves completion accuracy for:

Function Body Completion

Write the function signature and the return statement — Granite Code fills in the implementation logic with awareness of both.

Error Handling Insertion

Insert try/catch blocks, input validation, or null checks into existing functions without breaking the surrounding logic.

Test Case Generation

Generate unit tests that fit between existing test fixtures with awareness of the test runner patterns already in use.

Documentation Insertion

Add docstrings, inline comments, and type annotations that match existing documentation style in the file.

FIM Prompt Format

Granite Code uses a standard FIM token format compatible with Ollama's API:

<fim_prefix>[code before cursor]<fim_suffix>[code after cursor]<fim_middle>

IDE integrations like Continue.dev handle this formatting automatically — developers interact through standard completion UI without configuring FIM syntax manually.
