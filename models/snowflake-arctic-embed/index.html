Built for Enterprise Retrieval, Not Just Benchmarks

Most embedding models are evaluated on MTEB and trained to maximize scores on its component tasks — a mix of retrieval, classification, clustering, and similarity tasks that approximate real-world needs but don't fully represent the specific challenge of enterprise document retrieval. Snowflake's research team took a different approach with Arctic Embed: they identified asymmetric passage retrieval — the specific task of finding relevant passages in large document collections from short natural language queries — as the primary enterprise use case and optimized directly for it.

The result is an embedding model family that consistently outperforms models of comparable or larger size on real enterprise retrieval tasks, particularly for English-language corporate document corpora including policies, procedures, contracts, technical documentation, and knowledge base articles. Arctic Embed v1 established strong baselines across five size tiers. Arctic Embed 2 (released late 2024) refined the training methodology to push retrieval quality further, particularly at the medium and large size points.

For organizations whose RAG deployment serves primarily English-language enterprise content and where per-query retrieval precision on corporate documents is the defining quality metric, Arctic Embed is a focused, well-engineered option that delivers its performance efficiently across a range of hardware budgets.

Arctic Embed Model Family on Ollama

Arctic Embed v1 — Established Baseline

arctic-embed:xs

Ultra-Lightweight

22M parameters, 384 dimensions, 512 token context. Designed for maximum throughput on minimal hardware. Fits alongside a generation model on a 2GB Lightsail instance with room to spare. Quality is adequate for high-volume, lower-precision retrieval workloads.

ollama pull snowflake-arctic-embed:xs RAM: ~88MB · Dims: 384

arctic-embed:s

Lightweight

33M parameters, 384 dimensions, 512 token context. A step up from XS with meaningfully better retrieval quality at modest additional RAM cost. Strong choice for high-throughput embedding pipelines where the XS retrieval quality ceiling is insufficient.

ollama pull snowflake-arctic-embed:s RAM: ~130MB · Dims: 384

arctic-embed:m

Mid-Tier Balance

110M parameters, 768 dimensions, 512 token context. The inflection point in the Arctic Embed family — meaningful quality jump from the small variants without the compute cost of Large. Solid for most enterprise RAG deployments on 4GB+ instances.

ollama pull snowflake-arctic-embed:m RAM: ~440MB · Dims: 768

arctic-embed:m-long

Extended Context

110M parameters, 768 dimensions, extended context support. The medium variant trained for longer document passages. Useful when standard 512-token chunking produces poor retrieval because relevant content spans longer passages.

ollama pull snowflake-arctic-embed:m-long RAM: ~440MB · Extended context

arctic-embed:l

Maximum v1 Quality

335M parameters, 1024 dimensions, 512 token context. The large variant delivers the highest retrieval quality in the v1 family and competes with BERT-large class models. Strong NDCG@10 on enterprise retrieval benchmarks at lower RAM than alternatives.

ollama pull snowflake-arctic-embed:l RAM: ~1.3GB · Dims: 1024

Arctic Embed 2 — Refined Generation

arctic-embed-2:137m

Recommended v2 — Speed

137M parameters, 768 dimensions. The v2 mid-size variant with improved training methodology over v1. Better handling of domain-specific enterprise vocabulary and more consistent retrieval across diverse corporate document types. Best starting point for v2 deployments.

ollama pull snowflake-arctic-embed-2:137m RAM: ~550MB · Dims: 768

arctic-embed-2:568m

Recommended v2 — Quality

568M parameters, 1024 dimensions. The v2 large variant represents Snowflake's current best for enterprise English retrieval. Refined contrastive training with harder negatives produces noticeably better discrimination on semantically similar but distinct passages — a critical quality for enterprise knowledge bases.

ollama pull snowflake-arctic-embed-2:568m RAM: ~2.2GB · Dims: 1024

v1 vs v2 guidance: If you are starting a new deployment today, begin with Arctic Embed 2. The 137M v2 variant is directly comparable to arctic-embed:m in compute requirements but delivers better retrieval quality on enterprise corpora due to improved training. The 568M v2 variant is the current quality leader in the family. Use v1 variants only if you have an existing deployment with characterized performance or specific size requirements the v2 family does not match precisely.

Who This Model Family is For

👤 Personal use

Snowflake Arctic Embed is useful if you want to build a personal semantic search layer over your own notes, PDFs, bookmarks, or research documents. The smaller variants (XS and S) run comfortably on a laptop and let you find information by meaning rather than exact keywords. Keep in mind these are embedding models — they do not chat or generate answers on their own. You will pair them with a generation model (such as Llama or Qwen) to create a full personal RAG system.

🏢 Business / team use

For internal knowledge bases, support ticket search, policy retrieval, or document search across SharePoint, Confluence, or shared drives, Arctic Embed delivers retrieval quality that competes with much larger commercial embedding APIs. Running it on-premise through NoCloudGPT means sensitive contracts, HR documents, and customer data never leave your infrastructure. The Arctic Embed 2.0 release adds strong multilingual retrieval, which is valuable for teams working with content in German, French, Spanish, Japanese, and other major languages.

⚙️ Developer & technical use

Developers building RAG pipelines will find Arctic Embed a strong default choice. It consistently ranks near the top of the MTEB retrieval leaderboard while remaining small enough to embed millions of chunks efficiently. The model family integrates cleanly with vector databases such as Qdrant, Weaviate, pgvector, and Chroma, and works well with LangChain and LlamaIndex. The 768- and 1024-dimensional outputs are practical sizes that keep vector storage costs manageable.

🔬 Data science & research

Researchers benchmarking retrieval systems will appreciate that Snowflake published detailed training methodology, including their negative mining and curriculum approach, making Arctic Embed a reproducible baseline. The 2.0 release introduced Matryoshka Representation Learning, allowing you to truncate embeddings to smaller dimensions with graceful quality degradation — useful for ablation studies and cost-quality tradeoff analysis. It serves as a credible open alternative to closed embedding APIs when reproducibility matters.

What Arctic Embed Does Well

🏢

Enterprise Document Retrieval

Trained with enterprise retrieval as the explicit optimization target, not as a side effect of general benchmark optimization. Corporate policies, procedures, HR documentation, technical manuals, and knowledge base articles are the core design use case.

📐

Right-Sized for Every Budget

Five size variants from 22M to 568M parameters cover every deployment scenario from a single 2GB Lightsail instance running alongside a generation model to a dedicated embedding service on modest hardware. No need to overprovision.

🎯

Asymmetric Retrieval Optimization

Specifically optimized for asymmetric passage retrieval — the pattern where short queries retrieve long passages. This is the dominant pattern in enterprise RAG. Models optimized for symmetric similarity or academic QA don't represent this pattern as well.

⚡

Efficient CPU Inference

Even the Large variants are derived from encoder-only architectures (BERT-family) that run efficiently on CPU. No GPU required to achieve strong retrieval quality in the medium and large variants — important for cost-sensitive private deployments.

🔬

Hard Negative Training (v2)

Arctic Embed 2 was trained with carefully mined hard negatives — passages that are topically related but semantically distinct from the correct answer. This produces embeddings that better discriminate between genuinely relevant content and plausible-but-wrong matches.

📋

Well-Characterized Performance

Snowflake published detailed technical reports with retrieval evaluation across multiple enterprise-relevant datasets. Performance behavior is well-documented, making it easier to predict how the model will perform on your specific document type before deployment.

LangChain Pipeline with Qdrant
from langchain_community.embeddings import OllamaEmbeddings from langchain_community.vectorstores import Qdrant from langchain_community.llms import Ollama from langchain.chains import RetrievalQA # Arctic Embed 2 for retrieval embeddings = OllamaEmbeddings( model="snowflake-arctic-embed-2:137m" ) # Build vector store from enterprise documents vectorstore = Qdrant.from_documents( documents=enterprise_docs, embedding=embeddings, location="http://localhost:6333", collection_name="corp_knowledge_base", distance_func="Cosine" ) # Generation model — separate from embedding llm = Ollama(model="llama3.1:8b") # Full RAG chain qa_chain = RetrievalQA.from_chain_type( llm=llm, retriever=vectorstore.as_retriever(search_kwargs={"k": 5}), chain_type="stuff" )
Chunking Strategy for Arctic Embed (512-token limit)
from langchain.text_splitter import RecursiveCharacterTextSplitter # Arctic Embed has 512-token max context # Use ~400 tokens per chunk with overlap for safety splitter = RecursiveCharacterTextSplitter( chunk_size=1600, # ~400 tokens at ~4 chars/token chunk_overlap=200, # ~50 token overlap for continuity separators=["\n\n", "\n", ". ", " ", ""] ) chunks = splitter.split_documents(raw_docs) # For m-long variant: can use larger chunks splitter_long = RecursiveCharacterTextSplitter( chunk_size=3200, # ~800 tokens chunk_overlap=400, separators=["\n\n", "\n", ". ", " ", ""] )
Multi-Tenant Corporate KB — Namespace Isolation
from qdrant_client import QdrantClient from qdrant_client.models import Filter, FieldCondition, MatchValue client = QdrantClient("http://localhost:6333") # Each department gets isolated namespace via payload filter # Embeddings from the same Arctic Embed model instance # but queries scoped by department metadata def search_department_kb(query: str, department: str, top_k: int = 5): query_vec = embeddings.embed_query(query) results = client.search( collection_name="corp_knowledge_base", query_vector=query_vec, query_filter=Filter( must=[FieldCondition( key="department", match=MatchValue(value=department) )] ), limit=top_k ) return results # HR team sees only HR docs, Finance sees only Finance docs # Same embedding model, same vector store, isolated retrieval

Separate Embedding and Generation Services

For production deployments using arctic-embed-2:568m or arctic-embed:l alongside an 8B+ generation model, running separate Lightsail instances for embedding and generation is the recommended architecture. The embedding service can be a 4GB instance handling batch ingestion and real-time query embedding. The generation service runs on a separate 8GB instance. Internal Lightsail networking connects them at no bandwidth cost. NoCloudGPT configures this two-instance architecture as a standard production pattern.

Use Cases Where Arctic Embed Excels

  • HR and people operations knowledge bases: Employee handbooks, benefits documentation, policy manuals, onboarding materials. Arctic Embed's enterprise retrieval optimization handles the formal, procedural language of HR documentation particularly well.
  • IT service management and technical documentation: IT knowledge bases, runbooks, troubleshooting guides, and system documentation. The asymmetric retrieval training means a casual user question reliably finds the relevant formal documentation passage.
  • Legal and compliance document retrieval: Contract clauses, regulatory requirements, compliance policies, and legal precedents. Hard negative training in v2 helps discriminate between similar-but-distinct compliance requirements — a critical quality for legal retrieval.
  • Financial services internal knowledge: Investment policies, risk management frameworks, trading procedures, and regulatory filings. For English-language financial document retrieval where multilingual capability is not required, Arctic Embed delivers strong precision.
  • Manufacturing and operations documentation: Standard operating procedures, quality control documentation, equipment manuals, and safety guidelines. High-volume embedding of dense technical content benefits from the XS and S variants' throughput efficiency.
  • Customer-facing support knowledge bases: Product documentation, FAQ databases, and troubleshooting guides. The M variant running on a 4GB instance can handle real-time retrieval for customer-facing RAG applications at the query volumes typical of mid-sized support operations.
  • Research and intelligence platforms: Internal research reports, market intelligence briefs, and analyst notes where users need to query large archives of formal English business writing. Arctic Embed's training on enterprise-style content produces better results than models trained primarily on web text.

Arctic Embed's honest positioning: For English-language enterprise retrieval with the 512-token context window constraint, Arctic Embed 2 is among the best options available at its size tier. Its limitation relative to BGE-M3, Nomic Embed, and Qwen 3 Embedding is the 512-token context ceiling — if your documents require longer passages, you will need to chunk aggressively or choose a model with longer context. Deployment with Ollama — Complete Setup

# ── Step 1: Install Ollama ──────────────────────────────────
curl -fsSL https://ollama.com/install.sh | sh

# ── Step 2: Pull Arctic Embed variants ─────────────────────
ollama pull snowflake-arctic-embed:xs # 22M — ultralight
ollama pull snowflake-arctic-embed:s # 33M — light
ollama pull snowflake-arctic-embed:m # 110M — mid
ollama pull snowflake-arctic-embed:m-long # 110M — extended context
ollama pull snowflake-arctic-embed:l # 335M — v1 large
ollama pull snowflake-arctic-embed-2:137m # v2 mid — recommended
ollama pull snowflake-arctic-embed-2:568m # v2 large — max quality

# ── Step 3: Start Ollama as background service ──────────────
ollama serve &

# ── Step 4: Verify embedding endpoint ──────────────────────
curl http://localhost:11434/api/embed \
  -H "Content-Type: application/json" \
  -d '{
    "model": "snowflake-arctic-embed-2:137m",
    "input": "What is the company vacation policy?"
  }'

# ── Step 5: Install Qdrant for vector storage ───────────────
docker run -d --name qdrant \
  -p 6333:6333 \
  -v $(pwd)/qdrant_storage:/qdrant/storage \
  qdrant/qdrant

# ── Step 6: Create collection with correct dimensions ───────
curl -X PUT http://localhost:6333/collections/enterprise_kb \
  -H 'Content-Type: application/json' \
  -d '{
    "vectors": {
      "size": 768,
      "distance": "Cosine"
    }
  }'

# Note: use size 1024 for arctic-embed:l and arctic-embed-2:568m
