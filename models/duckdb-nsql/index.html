DuckDB-NSQL: Natural Language SQL for Analytical Workloads, Deployed Privately

DuckDB has become the default engine for local analytical workloads — fast, embedded, requiring no server, and capable of querying Parquet files, CSVs, and in-memory datasets with full SQL expressiveness. The gap it has not closed on its own is natural language access: data analysts who can describe what they want in plain English still need to translate that description into DuckDB's specific SQL dialect, including its analytical extensions and syntax preferences that differ from standard SQL in meaningful ways.

DuckDB-NSQL fills that gap. A 7B model fine-tuned specifically on DuckDB SQL by Numbers Station, it translates natural language questions into accurate DuckDB-dialect queries against provided schemas. Available via ollama run duckdb-nsql, it runs on CPU-only hardware, requires no GPU, and keeps your data schemas and query history entirely on-premise — no cloud API, no schema transmission, no data governance exposure.

What DuckDB-NSQL Does Well

  • DuckDB-specific SQL generation: Fine-tuned on DuckDB's dialect rather than generic SQL — correctly uses DuckDB's analytical functions, syntax patterns, and extensions that general-purpose models frequently misapply
  • Analytical query construction: Strong performance on the aggregation-heavy, window-function-rich queries that characterize analytical workloads — GROUP BY, PARTITION OVER, QUALIFY, and DuckDB's PIVOT syntax
  • File-based schema awareness: Generates queries against Parquet files, CSV datasets, and in-memory tables when schema context is provided — matches the actual DuckDB use pattern rather than assuming a traditional database server
  • Lightweight deployment: At 7B parameters and Q4 quantization, runs on 4–6GB RAM with no GPU requirement — fits on any analyst's laptop or a minimal cloud instance
  • Query explanation: Translates existing DuckDB queries into plain language descriptions for documentation, onboarding, and cross-team communication
  • Iterative query refinement: Supports follow-up prompts that modify a generated query — "now filter to only rows where X" — maintaining schema context across a multi-turn session

Deployment Requirements

Local Analyst Workstation — 7B Q4 (4–6GB RAM, CPU only)

DuckDB-NSQL is a single-variant deployment — the 7B Q4 model is the standard release and is designed to run on analyst hardware without GPU requirements. On a laptop or workstation with 4–6GB of available RAM, it provides interactive natural language query generation with response times of 5–15 tokens per second on modern CPU hardware. This is fast enough for the iterative exploration pattern typical of analytical work — ask a question, review the generated query, execute it in DuckDB, refine and repeat. Pull with ollama run duckdb-nsql.

Shared Team Instance — 7B Q4 (AWS Lightsail 4GB or CPU instance)

For teams that want a shared natural language query endpoint, DuckDB-NSQL runs comfortably on an AWS Lightsail instance with 4GB RAM — the lowest-cost shared deployment option in this model catalog. Multiple analysts can submit queries to a single Ollama endpoint without requiring dedicated GPU infrastructure. Lightsail 4GB instances run approximately $20–40 USD per month, making this one of the most cost-effective private AI deployments available for analytical teams.

The Real Cost of Analytical Schema Exposure

Analytical datasets frequently contain the most sensitive data an organization holds: revenue figures, customer cohort breakdowns, clinical outcomes, research results, and competitive intelligence. The schemas that organize this data — table names, column names, metric definitions — describe your analytical framework in terms that are meaningful to competitors and regulators alike. Sending this schema context to a cloud API as part of every natural language query creates an exposure surface that most data governance frameworks have not explicitly addressed.

DuckDB-NSQL on-premise means your analytical schemas never leave your local environment. The questions your analysts ask, the dataset structures they query against, and the patterns in their query history stay within your infrastructure boundary. For organizations handling financial data under SOC 2, clinical data under HIPAA, or proprietary research data under internal classification policies, local deployment is the only deployment model that satisfies governance requirements.
